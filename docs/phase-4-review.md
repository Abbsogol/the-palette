# Phase 4 — lifecycle, retries, and cross-feature review

**Status: open; not release-ready.** Reviewed September 27, 2026, from `ceba535` on `codex/phase-1-foundation`. Nine new failing reproductions identified **eight application defects**. Their fixes and regression coverage are included on the review branch in draft PR #1; deployment remains pending. Final local verification: **294 automated tests and 16 browser checks passed, with no failed or skipped tests.** Install, lint (zero warnings), and production smoke build passed. These results do not certify the managed services or the Ubuntu CI run for these changes.

The review read implementation and tests together. Existing green tests covered invitation creation but not an invited member actually reading the board; generation compensation but not request identity across retries; reminder authentication but not interrupted delivery; and paid checkout fulfillment but not a terminal delayed-payment failure. Additional tests assert stored rows and visible outcomes, not only mocked method calls.

## Reproductions and corrections

| ID | Risk | Reproduced behavior | Correction and evidence |
|---|---|---|---|
| P4-01 | P1 onboarding | Signup returned a user without a session when confirmation was required. The UI immediately made an unauthenticated profile write, displayed Unauthorized, and lost the creator/salon choice. | The signup request carries only the allowed initial type/name; the database user trigger persists them with ordinary defaults. Sessionless signup shows the email-confirmation step; immediate sessions proceed to onboarding. Metadata cannot grant admin, paid tier, credits, or completed onboarding. Component, SQL, and actual browser-SDK response tests cover both paths and failures. |
| P4-02 | P2 permissions/functionality | An owner could invite a member, but that member read zero private-board rows and zero board entries under `authenticated`. | Membership grants read access to the board and visible designs. Invitations, edits, and removals remain owner-controlled. Anonymous users/strangers, private drafts, member privilege escalation, leaving, revocation, and public visibility are checked under real DB roles. |
| P4-03 | P1 credits/cost | Repeating the same generation request id created another image and spent another credit. The route ignored the id and generated a new one. Process termination could also leave an unbounded hold. | A persisted client intent and server payload fingerprint claim one worker. Duplicates return pending or the stored result, and never release someone else's running claim. Two-minute leases, a shorter upstream timeout, and recovery on status reads/new claims/deletion bound abandoned holds. Completion after expiry is rejected. Tests cover concurrent retries, ownership, changed prompts, lost commit acknowledgments, expired paid/free holds, and deletion. |
| P4-04 | P2 delivery | An interruption after marking a booking reminded but before notification insertion left `reminder_sent_at` set with no reminders. Email failures were also discarded. | One DB transaction claims the booking, inserts both notifications, and queues email jobs. Email workers use leases, immutable recipient/payload snapshots, provider idempotency keys, and retryable acknowledgments. Tests cover rollback, concurrent schedulers, partial delivery, lost responses, old lease tokens, unavailable Auth, cancellation, and over-age ambiguity. Hosted retry scheduling remains open below. |
| P4-05 | P1 financial interaction | Buy one credit → reserve generation → refund the purchase → generation fails. Balance incorrectly returned to one. | Refunds reverse eligible pending paid holds as well as spendable balance. Release/recovery cannot resurrect a reversed hold. Profile-first locks serialize refund, completion, recovery and release. Both event orders, concurrent execution, partial refunds, free regeneration, unrelated new grants and duplicate events pass. Existing treatment of already-consumed credits is preserved; no new debt policy is introduced. |
| P4-06 | P2 privacy | Signing out left the previous user's private board title/content rendered. | Board detail and list subscribe to auth changes, clear private state, and reject responses belonging to an earlier load/session. Tests cover logout and a delayed private response arriving afterward. RLS revocation is verified separately. |
| P4-07 | P1 payment recovery | `checkout.session.async_payment_failed` was acknowledged without clearing the durable checkout. Failed credit/deposit payments blocked retry and account deletion. | Payment-mode failure/expiry handling rechecks current Stripe state, atomically records the terminal outcome and closes only the matching attempt. Deposit metadata now carries the attempt identity, including the lost-create-response path. A stale failure cannot erase a newer checkout or a paid receipt. Credit/deposit pages display failure/expiry and stop polling. SQL/route tests cover duplicate/delayed failures, partial persistence, rollback/retry, ownership, deletion and forbidden browser RPC access. |
| P4-08 | P2 financial UI | A fully refunded credit receipt still returned `fulfilled`, allowing the page to say “Credits added.” | Credit status distinguishes recorded credit reversals from fulfillment; the page shows “Refund recorded” and the current balance. The result component is scoped to its checkout id. This uses the credit-reversal ledger, not a statement of the bank's refund settlement or exact refunded money. |

Tests: `tests/phase4/lifecycle.test.js`, `payment-terminal-states.test.js`, `signup.test.jsx`, `board-session.test.jsx`, `generation-client.test.js`, `payment-outcomes.test.jsx`, and `tests/e2e/signup.spec.js`. Existing regression assertions remain enabled; the generation and reminder doubles were updated to the new RPC contracts.

Two **test-infrastructure issues** also appeared during the full run and were corrected: webhook event receipts were not cleared between the new payment tests, and separate native test databases concurrently altered shared PostgreSQL roles. Fixture setup now clears receipts and serializes cluster-role setup using a lock on the common local control database. The lock is released before tests run, so the application's concurrency tests still use concurrent connections. These are separate from the eight application findings.

## Remaining release and completion gates

1. **Isolated hosted staging is still missing.** The last verified Vercel Preview shares Production variables. No isolated Supabase/Stripe account identifiers were supplied. The Stripe connector was checked again in Phase 4 and still requires reauthentication. Production is not an acceptable substitute for synthetic billing/deletion tests.
2. **Reminder operations are incomplete.** The durable outbox fixes transaction loss, but `vercel.json` still schedules only one daily invocation. Failed emails need a supported frequent worker/manual retry before their deadline; pending jobs on the appointment day are skipped, and ambiguity older than 23 hours is held for review. Confirm the hosting plan, configure the scheduler secret/provider, and add monitoring/reconciliation before promising automatic email retries. No schedule or live mail configuration was changed.
3. **Provider and financial exceptions remain.** Rehearse real payment success/failure/3DS/delayed methods, cancellation and late-deposit automatic refunds. Subscription-mode incomplete/failed checkouts are not handled by the new payment-mode failure cleanup; recovery must consider the real subscription state, not blindly delete a reservation or cancel a potentially paid plan. Disputes and subscription-invoice refund policy, failed/action-required refunds, unknown Prices/paginated invoices, and exhausted webhook delivery need supported operator workflows.
4. **Historical reconciliation remains mandatory.** Backfill/reconcile prior payment, subscription-period and boost identities and outstanding refunds before replaying events. Before migration 007, inspect existing reserved generations alongside credit refunds: older refunds may already have missed a held credit. The migration changes future accounting and does not invent historical allocations.
5. **Recovery and privacy need hosted verification.** Full managed schema export/replay, isolated backup restore, actual Storage deletion/races and orphan cleanup remain open. Generation recovery is lazy on subsequent status/claim/deletion requests, not a continuously running recovery daemon. Browser privacy improvements here cover boards; they do not certify every mounted screen through every session transition.
6. **Remote verification and deployment are pending.** Run Ubuntu CI for the exact Phase 4 commit, then rehearse all migrations and services in isolated staging. These local checks do not authorize a production rollout. The user-visible “refund recorded” credit state reflects credit reversals; extremely small monetary refunds rounded to zero credits are not represented by that ledger and still need a monetary receipt model if the UI must show every refund.

Apply migrations **001–008 in order** against a complete rehearsed baseline. New generation/status/reminder/payment routes depend on migrations **006–008** and must not deploy before them. Stop/quiesce old generation workers during the coordinated migration/app rollout; do not reinterpret a still-running legacy request as abandoned. Reconcile old holds/refunds first. Existing phase reports and the recovery runbook remain applicable; no earlier phase is declared complete by this report.

Provider contracts consulted: [Stripe delayed payment events](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted), [Checkout Session states](https://docs.stripe.com/api/checkout/sessions), and [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys). Resend documents a 24-hour key window; the outbox stops blind replay earlier. Documentation and installed SDK types establish contracts, not account connectivity.
