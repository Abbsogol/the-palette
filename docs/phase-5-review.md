# Phase 5 — account boundaries, recovery and refund settlement

**Status: open; not release-ready.** Reviewed September 27, 2026, from `4fcfa34` on `codex/phase-1-foundation`. This review inspects implementation and previous tests together. New regression tests first reproduced failures; fixes were then checked independently and integrated. This report records the pre-publication verification snapshot; subsequent remote CI results are recorded in [draft PR #1](https://github.com/Abbsogol/the-palette/pull/1). It is not a claim that migrations or provider configuration have been applied.

## Findings and corrections

| ID | Priority | Reproduced defect | Correction / evidence |
|---|---|---|---|
| P5-01 | P1 | A completed subscription checkout whose subscription became canceled or incomplete_expired permanently blocked another checkout and deletion. Expiry after a lost session-save also left a reservation. | Verify current session, subscription, customer, user and attempt before atomic exact-attempt release. Creation, deletion, failure/expiry events and terminal lifecycle events recover it; unrelated or newer payable attempts survive. `subscriptions.test.js` checks retries, concurrent calls, lost saves, identity mismatches and real database state. |
| P5-02 | P1 | An unpaid subscription retained paid entitlements after collection retries ended. Simply clearing the tier would have allowed deletion and hidden billing recovery. | Revoke the tier while retaining billing identity; block deletion/new subscriptions for nonterminal relationships and expose billing management to existing customers. SQL, route and billing UI checks cover the interaction. Past-due grace policy is preserved; it is not presented as a freshly confirmed activation. |
| P5-03 | P2 | A historically paid subscription checkout reported activation even when the current subscription was unpaid, paused or on a different Price. Moving between checkout URLs retained old success messages; deposits had the same stale-result problem. | Require matching current provider plan/status and stored identity; show terminal/payment-required outcomes. Key result state by checkout/booking. `subscription-outcomes.test.jsx`, `refund-outcomes.test.jsx`. |
| P5-04 | P1/P2 | Private profile details, generated images and financial outcomes remained visible after logout/account switching; old reads could overwrite the newly signed-in account. | Clear/remount account-owned UI, invalidate stale loads and scope results to authenticated identity. Same-account token refresh preserves ongoing work. `auth-lifecycle`, `generation-session`, `checkout-session`, `boost-outcomes` tests. This coverage is for these screens, not every mounted app component. |
| P5-05 | P1/P2 | An old onboarding/profile/generation form could fetch a new account's bearer token and write or spend against that account. Password recovery through the global SDK had an equivalent session-lock race. A delayed boost checkout response could redirect after logout/account switching. | Bind actions to the displayed account, compare fresh identity, and ignore stale completions. Password update uses the captured user's bearer token against the ordinary Supabase Auth endpoint. No hosted password was changed. |
| P5-06 | P2 | Onboarding committed and navigated away while referral application ran unobserved; a failure silently lost rewards and a visible retry path. | Await referral application before completion and surface errors. Real SQL asserts once-only rewards and additive onboarding grants through lost acknowledgments and retry; UI retains the form. |
| P5-07 | P2 | Buying another generation from the regeneration screen kept the old root and exhausted-free flag, hiding the new paid generation's free regeneration. | Reset the paid root and its free entitlement; the next free request names the new parent. `generation-session.test.jsx` asserts the paid → free → paid → free sequence. |
| P5-08 | P1 | A full manual refund before delayed deposit fulfillment caused another refund request and permanent webhook failure. A pending manual partial refund plus a successful automatic remainder falsely reported the entire deposit refunded. Pending credit/boost refunds also revoked entitlements too early. | Reconcile authoritative captured money against all current refunds, including untagged/manual ones. Only successful cumulative amounts reverse credits or completed boost/deposit entitlements. Tiny monetary refunds remain visible even when credit rounding is zero. Late canceled/declined deposits retain the user's automatic-full-refund policy. |
| P5-09 | P1 | A refund failing after an earlier success could still appear settled and permit deletion. During implementation, independent review reproduced new guard gaps after an unsuccessful provider read and during a new check of an already-refunded deposit. A pending ordinary refund handed to late-deposit recovery could also leave a permanent deletion block. | Keep provider settlement state separate from already-applied entitlement reversals; unresolved failures/reads require review and prevent deletion. Claims serialize with deletion through the profile lock; leases fence stale workers. Both refund records settle atomically at the late-deposit handoff. No automatic recrediting, rebilling or retry of a failed bank refund is invented. |
| P5-10 | P2 | Reminder jobs claimed before cancellation still sent after cancellation committed during recipient lookup. | Recheck the booking immediately before preparing the immutable send payload; canceled/elapsed-date jobs are skipped. A cancellation after the external send starts cannot retract an email. |
| P5-11 | P1/P2 | Authenticated clients could bypass the booking UI and insert appointments during closed hours, on inactive/unconfigured days, off the offered half-hour grid, or on past dates. | Database insertion validates working hours and slot alignment as well as the existing service/duration/overlap constraints. Dates unambiguously past in every time zone are rejected. Exact local-day and elapsed-time checks remain open because creator time zones are not modeled. Existing bookings remain cancellable after availability changes. |

The recorded red scenarios are not a count of independent defects: several deliberately exercise the same defect through different orderings. Reports under ignored `.backups/phase5-*-before.json` retain failures. Temporary test-selector/syntax errors were corrected before interpreting reproduction evidence. Existing fixtures were strengthened with actual session identities, availability, captured payment amounts, refund amounts/statuses and refund histories; assertions on balances, booking state and entitlements were preserved.

## Real services versus doubles

Database tests execute migrations and SQL role checks, but their catalog-derived fixture is not a complete managed Supabase clone. SQL transport doubles do not reproduce PostgREST projection, relation joins, limits, JWT refresh or Storage bytes. This review specifically caught a proposed UI use of profile columns absent from the actual profiles view; the implementation instead uses its existing owner-masked customer identity.

Stripe calls and injected event payloads are doubles. Existing installed-SDK signature tests still run. New mocks model captured amounts, manual/partial/pending/failed refunds and provider read failures; they do not establish live account mode, configured events, idempotency retention, real bank behavior or eventual consistency. Browser tests render the production Next build, with intercepted/fake external services. Component tests assert visible privacy, outcomes and actions; they are not evidence of real hosted payment/password changes.

Stripe distinguishes unpaid access from a still-existing billing relationship, and refund creation from eventual success or failure. These contracts informed the tests and fixes. [Subscription lifecycle](https://docs.stripe.com/billing/subscriptions/overview), [refund creation](https://docs.stripe.com/api/refunds/create), [failed refunds](https://docs.stripe.com/refunds#failed-refunds).

Vercel `sogol-s-projects1/the-palette` is Hobby and still has the same nine variables scoped to Production and Preview; no CRON_SECRET is listed. Secret values were not opened. The user does not know of a staging environment. The Stripe connector still requires reauthentication. No staging/paid resource was provisioned.
2. **Managed verification remains blocked.** Confirm an isolated Supabase project, a Stripe sandbox, staging app/redirects and synthetic accounts before card/3DS/delayed payment, renewal, refund, Auth, Storage, deletion or restore tests. Production and its shared Preview are not synthetic integration targets.
3. **Booking time is not fully specified.** The app renders the visitor's local calendar, but the database previously used UTC dates and no creator zone exists. The user was asked whether to use each creator's zone or Dubai globally. Working-hour/grid enforcement is implemented; the new past-date guard conservatively permits yesterday UTC because it can still be today locally. Exact local past-day/same-day validation, timezone/DST and reminder deadlines remain unresolved. Phase 5 is not complete with this gap.
4. **Operations and history are outstanding.** Rehearse migrations 001–012 on a complete managed baseline before the dependent app. Reconcile historical purchases, held credits, subscription periods, boosts and refunds; new refund-state tables cannot infer old bank failures. Provide an operator workflow for review states and failed/exhausted webhook delivery. No automatic financial adjustment policy beyond the already-approved late-deposit refund was introduced.
5. **Reminder and recovery deployment remain open.** Configure a supported retry worker cadence, secrets and alerts; the current daily cron does not prove timely retries. Complete managed backup/Storage export and restore rehearsals and actual upload/deletion races. Generation recovery remains lazy.
6. **Exact-code Ubuntu CI is still required before release.** Local macOS/native PostgreSQL results cannot certify another environment. Keep the PR draft and retain all earlier unresolved gates.

No production migration, production payment/refund, hosted password update, live email, destructive hosted test or production deployment was performed in Phase 5.
